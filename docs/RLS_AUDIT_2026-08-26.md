# Cliniverse RLS Audit — 2026-08-26

## Verified production findings

- RLS is enabled on `profiles`, `subscriptions`, `case_completions`, `mcq_answers`, `evaluation_cases`, `pulse_questions`, and `nexus_cases`.
- `profiles` currently has permissive public policies allowing any role to select, insert, and update rows.
- `subscriptions` currently has an insert policy named `Service role can insert subscriptions`, but it applies to `public` with `with check (true)`, so the policy is not actually restricted to the service role.
- `subscriptions` also has an own-user SELECT policy based on `auth.uid() = user_id`.
- `case_completions`, `mcq_answers`, `pulse_questions`, and `nexus_cases` have RLS enabled but no visible policies in `pg_policies`.
- `evaluation_cases` has service-role-only CRUD policies.

## Risk assessment

### P0
- `profiles` public SELECT/INSERT/UPDATE breaks user-data isolation and must be replaced before real identity or healthcare-adjacent user data is enabled.
- `subscriptions` insert policy is overly broad and must be restricted to `service_role`.

### P1
- `case_completions` and `mcq_answers` need authenticated own-row policies before the real auth flow is wired.
- Current application types and database schema are not fully aligned; for example `UserProfile` includes an `email` field while the verified `profiles` table schema does not expose an `email` column.

## Prepared remediation

Migration `supabase/migrations/001_user_data_rls_hardening.sql` replaces the verified permissive policies with authenticated own-row policies and restricts subscription insertion to `service_role`.

## Release gate

Do not apply this migration to production until:
1. Real Supabase Auth wiring passes preview build and sign-in tests.
2. Existing profile creation flow is reviewed against `auth.uid()` ownership.
3. Subscription webhook/service-role path is verified.
4. Rollback SQL is prepared.
5. A production migration window is explicitly approved.
