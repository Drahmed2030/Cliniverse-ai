## 1. Service-worker change while the probe is pending — fixed
`createWorkerGuard(env).check()` takes a snapshot (controller object, list of active workers, a `controllerchange` epoch), probes, inspects caches, then re-reads the registrations and the controller. If **anything differs** (a `controllerchange` fired, a different controller object, a different set of active workers) the evaluation is **discarded** and repeated; after `maxAttempts` (4) without a stable result the outcome is **`blocked`** (fail closed). Only a stable evaluation can lead to `clean` or to any side effect. After `clean`, `stillCurrent()` must hold **immediately before the tokens are used**; `recoveryRun` re-checks (bounded: 3) and blocks if it never becomes current. Tests (real code, fake browser): controller swapped to an **old** worker while the previous controller's probe is pending ⇒ not clean (→ cleanup/reload); swapped to a **current** worker ⇒ first result discarded, re-check clean, no cleanup triggered; active-worker set changes without an event ⇒ discarded; change **after** a clean result ⇒ `stillCurrent()` false and the re-check sees the old worker; changes that never settle ⇒ blocked with no side effects; unavailable registrations (throws): current controller clean, stale controller ⇒ reload then blocked, no controller ⇒ clean.
Limit: the check cannot close a window of zero length — a worker could still take control after the last synchronous confirmation and before the first network call. That requires an installed-but-waiting old worker to activate and claim at that instant; the recovery client's only calls are to Supabase. Not reproducible in a real browser; covered by the confirmation above, not eliminated.

## 2. Page life cycle — cancellation added
`recoveryRun.ts` owns the sequence guard → read fragment → strip → recovery client → `setSession` → form/submit. `cancel()` (called by the effect cleanup) sets a flag and disposes the guard. After cancel **nothing new** is started: no guard side effect (unregister, cache delete, reload), no fragment read, **no `history.replaceState`**, no recovery client, no request, **no view update**; `submit()` returns `cancelled`. The parsed link lives in a `linkStore` that survives a remount, so under React StrictMode (mount → cleanup → mount) the fragment is read and stripped **exactly once** and `setSession` runs once (the old `started` ref, which would have blocked the second mount after a cancel, is gone).
**What cancellation does not do (stated, not claimed):** a request already sent (`setSession`, the probe, `unregister`, a cache delete, `updateUser`) is **not cancelled** — the clients offer no way to do that; only its consequences are dropped (the result is ignored, no state is written). **One deliberate exception:** once the password-update request has been sent, the global sign-out that follows still runs even if the page was left, because skipping it would leave other sessions alive; it writes no UI and no history.
Tests: delayed guard → unmount; unmount after `blocked` / `reloading`; unmount during `setSession`; unmount during the password update (UI silent, sign-out of the sent update completes); StrictMode-style remount (one read, one strip, one `setSession`); superseded run cannot write; blocked/never-current clean results strip the fragment but never parse or use it.

## 3. Cache deletion — verified, fails closed
A cleanup is now: unregister stale registrations → delete the legacy Cliniverse caches → **re-list and verify** none remain. A delete that rejects, returns `false` or reports success without removing the cache, a listing that fails (before or after), or any leftover ⇒ **`blocked` immediately** (no reload that could mask it). The same inspection runs on **every** load, so a deletion that did not survive the reload (marker present, legacy cache still listed) ⇒ blocked even with no stale worker. One reload only; a stale worker or dirty cache after it ⇒ blocked. Only Cliniverse-owned caches (`/^cliniverse/i`, other than the current `cliniverse-static-v4`) are ever deleted; the current cache and unrelated caches (`workbox-*`, `my-app`, …) are untouched (tested). No Cache API at all ⇒ nothing stored ⇒ clean.
Tests: delete rejects / returns false / lies / listing rejects (first and second call) / lingering after reload / success / unregister rejects or returns false / marker + stale worker / only-owned-caches.
